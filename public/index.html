AI Trace

See the hidden characters, chat-app leftovers and provenance metadata that ChatGPT, Gemini, Claude, Grok and image generators leave in text and files, with the exact bytes behind every finding, and get a clean copy to compare. Everything runs in your browser. Nothing you paste or open is uploaded.

Original, findings marked

Statistical watermarks such as Google's SynthID Text are carried by the choice of words, not by characters, so they do not show here. See How detection works.

This page reads the bytes of what you paste or open, in your browser. There is no model and no server. Every finding comes from one of the rules below, and every image finding names the byte range it came from, so you can check it with a hex editor or another tool.

Text

The rules run in this order. Where two matches overlap, the earlier rule wins, so a whole citation marker is claimed before the private-use characters inside it. Hidden messages in tag characters and variation selectors are decoded and shown.

Images: walking the file

The file is read as a list of blocks, the way a decoder reads it. Blocks a decoder needs to draw the picture are kept and copied byte for byte. Every other block is metadata: it is listed with its offset, its raw bytes and what it says, and left out of the clean copy. Nothing is re-encoded, so the clean image has exactly the same pixels. One block is added back: when a JPEG's EXIF says the photo is rotated, the clean copy gets a 36-byte EXIF block that holds only the rotation, so it is not shown on its side.

C2PA content credentials, step by step

C2PA (the Coalition for Content Provenance and Authenticity) defines a signed record of where a file came from. OpenAI, Google, xAI, Adobe and others attach one to generated images. This page reads it like this:

  1. Find the store. In JPEG it is in APP11 segments (marker FF EB). Each segment starts with JP, a 2-byte box instance and a 4-byte sequence number, then the 8-byte header of the outer box (length and jumb), then data. Segments of one instance are put in sequence order and joined, keeping the box header only once. In PNG the store is the whole caBX chunk; in WebP the C2PA chunk.
  2. Walk the JUMBF boxes (ISO/IEC 19566-5). A box is a 4-byte big-endian length, a 4-character type and data. A jumb superbox starts with a jumd description box: a 16-byte type UUID whose first four bytes name the kind (c2pa store, c2ma manifest, c2as assertion store, c2cl claim, c2cs signature, cbor or json content), a toggles byte, and a null-terminated label when toggle bit 0x02 is set. Content sits in cbor, json, bfdb and bidb boxes. The JUMBF tree under each C2PA block shows every box found, with its label.
  3. Pick the active manifest. The store holds one manifest per signing step, oldest first. The last one describes the file as it is now; earlier ones are listed as earlier manifests.
  4. Read the claim. The claim (c2pa.claim or c2pa.claim.v2) is CBOR (RFC 8949). It names the claim generator, the software that signed, and lists the assertions it covers with their hashes.
  5. Read the assertions. c2pa.actions lists what was done: c2pa.created, c2pa.edited, c2pa.converted, c2pa.watermarked, each with a digitalSourceType (the IPTC term; trainedAlgorithmicMedia means a generative model made it), a softwareAgent and a time. c2pa.ingredient records source files. c2pa.hash.data is a SHA-256 hash over the file, leaving out the store itself. c2pa.soft-binding names a watermark or fingerprint that can find the credentials again after they are stripped.
  6. Read the signature. It is a COSE_Sign1 structure (RFC 9052, CBOR tag 18): protected header, unprotected header, an empty payload (the claim is what is signed) and the signature. Header 1 is the algorithm (-7 ES256, -35 ES384, -36 ES512, -37 PS256, -8 EdDSA). Header 33 (x5chain) holds the signer's X.509 certificates in DER, read here for subject, issuer and validity dates. sigTst in the unprotected header holds an RFC 3161 timestamp.
  7. What is not done here. The hash is not recomputed, the signature is not verified, and the certificate is not checked against the C2PA trust list, so a forged store is shown as written. To verify, use contentcredentials.org/verify or the open-source c2patool. The specification is at c2pa.org/specifications.

XMP and the IPTC AI label

IPTC's Digital Source Type vocabulary gives a standard label for synthetic media. In XMP it is written as Iptc4xmpExt:DigitalSourceType with a value such as http://cv.iptc.org/newscodes/digitalsourcetype/trainedAlgorithmicMedia (made by a generative model) or compositeWithTrainedAlgorithmicMedia (edited with one). The same terms appear inside C2PA actions. This page reports the label wherever it appears and names the block and byte offset.

SynthID and other pixel watermarks

SynthID is Google DeepMind's watermark for content from Google's models. For images it is added to the pixel values as the image is generated, and is designed to survive cropping, resizing, colour changes and compression. It is not stored in any block of the file, so nothing in the file's structure points to it, and removing metadata leaves it in place. Reading it needs Google's detector model, so no file reader, this one included, can see it. To check an image, ask the Gemini app whether it was made with Google AI, or use Google's SynthID Detector.

What this page can show is the metadata Google writes alongside the watermark: C2PA credentials and the IPTC label. When those name a Google model, or carry Google's AI label, the image report marks SynthID as likely. The same applies to the other pixel watermarks in the image report (Adobe TrustMark, Meta Video Seal and Stable Signature): the file may say one is there, but the watermark itself is only readable with its own decoder.

Why an image is still flagged after cleaning

Cleaning removes what the file says about itself: the C2PA record, the IPTC label, the tool names. A detector that still says "AI" after cleaning is not reading any of that. It is reading the pixels, and the clean copy has exactly the same pixels. This table shows which signals cleaning removes.

SignalWhere it livesRemoved by cleaning
C2PA content credentialsA metadata block (APP11, caBX, C2PA)Yes
IPTC label trainedAlgorithmicMediaXMP, or the actions inside C2PAYes
AI tool names and promptsEXIF, XMP, PNG text chunksYes
Pixel watermark (SynthID and others)Spread through the pixel values of the whole imageNo
The generator's own pixel statisticsEvery pixel the model drew. An AI edit usually redraws all of them, not only the part that changedNo
Image size on the generator's gridThe width and height, such as 864 × 1152: about 1 megapixel, both sides multiples of 32No
JPEG encoder settingsThe quantisation tables, which the image needs, so the cleaner keeps themNo
No camera EXIF at allAn absence: no make, model, lens or exposureCleaning makes this more noticeable, not less

Why the whole image counts, not just the edit. An image model does not paste a patch into a photo. It encodes the photo into its own internal form, generates a new one, and decodes every pixel again. The camera's traces go everywhere at once: the sensor's noise pattern, the pattern left by its colour filter, its sharpening and compression. In their place are the textures of the model's decoder. AI-image classifiers are trained on that difference, and a pixel watermark like SynthID is written across the whole frame as the image is decoded.

A worked example. A phone photo of an empty room, with a camera-app stamp of direction, position and time across the top, was edited with an image model to remove a wall socket and marks under the window. The copies we were sent had no metadata at all, so this page reports nothing for either, yet a detector still flagged the edit. Comparing the two files:

  • The edit is 864 × 1152: exactly 3:4, 1.0 megapixels, both sides multiples of 32. The original is 1200 × 1600, the kind of size a messaging app produces when it scales down a phone photo.
  • The edit is a baseline JPEG at quality 95 with the standard libjpeg tables (luminance row 2, 1, 1, 2, 2, 4, 5, 6), the usual output of a server-side encoder. The original is a progressive JPEG at quality 75.
  • The edit is a new image, not the original with a patch. After lining the two up, textured areas well away from the socket, such as the carpet, still differ from the original pixel by pixel. Only flat areas like the bare walls come close, because there is little there to change.

Which of these a detector used depends on the detector. A check in the Gemini app reads SynthID, which is there only if a Google model made the edit. Other detectors are classifiers that read pixel statistics, and may also weigh the size. None of them read the metadata this page removes, which is why the clean copy gets the same answer as the original edit.

How online AI-image detectors decide

These detectors read pixels, not metadata. A trained model scores the image, and nothing in a file can be pointed to as the reason.

  • DeepAI AI Image Detector, observed from its page code and network traffic on 11 November 2026. The page uploads the image to api.deepai.org/ai-image-detector-upload, then asks /ai-image-detector-query once a second until the job is done. The answer is one number from 0 to 100. At 50 or more the page says the image is likely created by AI. Confidence is High at 80 or more (or 20 or less), Medium at 60 or more (or 40 or less), and Low in between. Nothing is worked out in the browser and no reason is given: the number comes from a model on DeepAI's server, and a model like that scores an image in a fraction of a second on a GPU. The page also sends the same image to /analyze-image-for-ads to choose adverts, unless the account has paid to remove ads, and its "advanced analysis" links out to TruthScan.
  • TruthScan, from a result it gave for the worked example above. It returns a score, a heatmap and paragraphs of reasoning. The heatmap comes from the classifier. It colours, blue to red, the parts of the image that pushed the score up, most likely as a class activation map, the usual way to draw one. The reasoning reads like a language model describing the image after the verdict. It cited "synthetic text overlays" and the "lack of natural camera metadata", but the untouched original has the same camera-app stamp and no camera metadata either, so those points do not tell the two apart.

The AI-image model on this page

The Pixel check in the image report runs an open model of the same kind as DeepAI's and TruthScan's, in the browser. It decodes the original and the clean copy, compares them pixel by pixel, scores them and draws a heatmap on each, side by side, so you can see whether cleaning moved anything. When the pixels are identical, which is the usual case, the model runs once: identical input gives identical output.

  • Model. Community Forensics (Jeongsoo Park and Andrew Owens, CVPR 2025), a ViT-S/16 vision transformer trained on images from 4,803 generators, MIT licence. We fine-tuned it on 596 phone photos and 990 edits of them made with Grok's image editor, plus generated and real images from the Community Forensics dataset, so it sees a photo that an image model has regenerated, not only a fully generated image. Both sides were given random grain, sharpening and chromatic aberration in training, so ordinary camera-style processing is less likely to hide an edit. It is exported to ONNX with a second output for the heatmap and its weights stored as 8-bit integers: 23 MB, served with this page and run with ONNX Runtime Web in a worker. The image is not uploaded. How it was trained: docs/finetune.md.
  • Tiles. The model sees 384 × 384 pixels at a time. Shrinking a whole photo to that size wipes out the fine texture an edit leaves behind, so the page cuts the image into 384-pixel tiles at its own resolution and scores each one. Images over 3,072 pixels on the long side are scaled down first. The image score is the mean of the scores of the tiles on that 384-pixel grid.
  • The heatmap. Inside a tile the model works on 24 × 24 patches of 16 pixels and reads its verdict from one summary token that gathers them. The exported model also applies that same scoring head to every patch, so each 16-pixel patch gets a score from the model's own last layer, not from an extra model. Within a tile the patch scores are divided by their maximum and multiplied by the tile's score, so a tile the model calls camera-made stays blue whatever its patches rank. For the map, tiles also run halfway between the grid positions, every 192 pixels, and overlapping tiles are blended with weights that fall to zero at each tile's edge, so no seams show. Blue is 0, red is 100%.
  • The line. A mean of 60% or more is reported as looking generated. We set it from the tests below: at 60% every Grok edit was caught and no held-out phone photo was called AI.
  • Speed. After a one-time 23 MB download, each tile takes about a third of a second on a recent laptop. The heatmap needs a tile every 192 pixels, so 864 × 1152 (20 tiles) takes about 7 seconds, 1200 × 1600 (48 tiles) about 18, and a 12-megapixel photo, scaled to 3,072 pixels, about a minute (165 tiles). Phones are slower. The model runs once when both copies decode to the same pixels, and twice when they differ. The page is cross-origin isolated so the model can use several threads; it ran three times slower without.

The heatmap changed with it: on the Grok edits, 98% of tiles score 50% or more, against 30% before, so the map covers the regenerated photo instead of a few tiles. With grain, sharpening, white-balance drift, chromatic aberration, vignetting and JPEG applied together, it still called 36 of 51 edits AI; the model before that training change called none of them, so a deliberate post-process can still hide some edits. All the training edits came from Grok, so edits from other tools may score lower, and lossless film scans and screenshots are its weak spot. A score is a pointer, not proof.

In the worked example, the model as it was on 11 November 2026 scored the original 20%, under the line. Its heat sat on the camera-app stamp across the top, which is drawn by the app, and the room stayed cool. Before fine-tuning, the edit scored 29% and the original 1%; the grid tiles that scored highest on the edit were along the top, over the stamp and the ceiling, and TruthScan's heatmap for the same image weighted the bedding and the carpet instead. Two models trained on different data can agree on a verdict but only partly on where the evidence is, which is why a heatmap explains a score but does not prove it.

SynthID Text

For text, SynthID changes which words the model picks. A keyed pseudo-random function scores the candidate tokens at each step and sampling favours the high scorers. A detector holding the same key scores a passage; without the key the choices look like ordinary writing. Google released the method as open source in October 2024, but the keys used by Gemini are private. It leaves no characters behind, so the Text tab cannot see it, and rewording the text weakens it.

Limits

  • Missing metadata proves nothing. Most social sites and messaging apps strip it on upload, and many generators write none.
  • A name in the metadata is a lead, not proof: a camera made by Google writes "Google" too. The image report quotes the text around every name so you can judge.
  • C2PA hashes and signatures are read, not verified.
  • The AI-image model gives a score, not proof. It misses some generated images and flags some real photos, and so do the online detectors.
  • Only JPEG, PNG and WebP are parsed block by block. HEIC, AVIF, video and audio get a string scan only.
  • Typography rules (dashes, curly quotes) catch habits that many people share. They are off by default.
